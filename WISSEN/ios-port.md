# iOS port — spike results (2026-07-25)

Branch `ios-port-spike`. The shared C++/Obj-C engine runs on iOS. Verified in
the iPad Pro 11" simulator: config loaded, two FT senders up, clip decoded via
AVAssetReader, 200+ frames pushed per panel, preview rendering, status server
answering on :8080.

Dropping FFmpeg/SDL2 for the native Apple AV stack is what made this cheap —
AVAssetReader, AudioQueue, CoreMIDI and CoreBluetooth are identical APIs on
both platforms.

## What is shared

`ios-app/` builds the **same** `src/` files and the **same**
`mac-app/MidiFtBridge/EngineBridge.{h,mm}` as the Mac target — nothing is
copied. Only the SwiftUI layer is separate. `EngineBridge` is Foundation-only
(no AppKit), so it ported untouched.

Both targets are generated by xcodegen:

    cd ios-app && xcodegen generate
    xcodebuild -project MidiFtBridgeIOS.xcodeproj -scheme MidiFtBridgeIOS \
      -sdk iphonesimulator -destination 'generic/platform=iOS Simulator' build

`MFB_NATIVE_MACOS=1` is still the flag on both targets. It means "native Apple
AV stack, no FFmpeg" — the name predates iOS. Genuine platform differences
switch on `TARGET_OS_IPHONE`.

## The bug the iPhone found (fixed)

Running on device segfaulted (signal 11) after a few rapid clip switches. It is
**not an iOS bug** — it is a use-after-free that has always been in the engine:

- the render loop took `m_clipMutex`, called `getCurrentFrame()` (which returns
  a pointer *into* the ClipPlayer's own buffer), then **released the lock**;
- it then read through that pointer for the UI callback and every panel's
  `extractRegion`;
- `triggerMapping()` takes the same lock and does `m_activeClip.reset()`,
  destroying that buffer.

Any tap during a render freed memory the worker was mid-read on. macOS survives
it because its allocator usually keeps the freed page mapped (worst case a
glitched frame); iOS returns pages promptly, so it faults immediately.

Fix (`engine.cpp`): copy the canvas into a worker-owned `m_canvasBuffer` while
still holding the lock, then work from the copy. The lock is deliberately *not*
extended over the UDP sends — that would let network syscalls block triggers.

The same bug explains the earlier crash on a **missing** clip: `triggerMapping`
resets the active clip before discovering the file will not open, freeing the
buffer on the way out.

## What had to change (4 places)

1. **`audio_output_macos.mm`** — the CoreAudio HAL (`AudioObjectGetPropertyData`,
   `kAudioHardwarePropertyDevices`) is macOS-only. iOS gets an AVAudioSession
   implementation behind the same pure-C++ surface, plus `prepareForPlayback()`
   which sets the Playback category and activates the session (an AudioQueue on
   iOS is silent otherwise).
2. **`clip_player_macos.mm`** — `kAudioQueueProperty_CurrentDevice` is macOS-only;
   compiled out for iOS.
3. **`engine.cpp` `sshShutdown()`** — `popen` + the `ssh` binary. Neither exists
   for a sandboxed iOS app.
4. **`status_server.cpp`** — `system()` is marked unavailable on iOS. Only the
   fallback branch used it (the engine callback is always wired in practice).

The Mac Release build was rebuilt after all four and still succeeds.

## Feature losses on iOS — need decisions

- **No audio output device picker.** iOS resolves the route itself by priority
  (USB > BT > headphones > speaker). Attach the Fantom and it *becomes* the
  route, but you cannot choose between several attached outputs, and the
  `audio_output` config key becomes a check rather than a command.
- **No panel shutdown.** Would need an in-app SSH client (a third-party
  dependency this project has avoided) or a small HTTP endpoint on the panels.
  Currently reports the limitation instead of silently failing.
- **Status server is foreground-only.**

## Verified on a real iPhone 15 Pro

Signed with the personal team (`DEVELOPMENT_TEAM: PRM2DDW7M5`) and run on
device. CoreMIDI enumerated and connected (`Connected to Netzwerk Session 1`),
CoreBluetooth powered on and scanned for the iPixel panel, all 13 clips
triggered and played through AVAssetReader, status server bound.

## Untested — the real risks

- **Local network permission.** The simulator does *not* enforce the iOS 14+
  gate; a real device does. Unicast UDP to 192.168.10.x will prompt, and a
  denial means panels silently receive nothing. The app needs to surface that
  state itself. `NSLocalNetworkUsageDescription` is set. **Not yet confirmed
  that frames actually reach the panels** — the panels were not powered during
  the device test, and the phone's status server is not reachable from the Mac
  (devicectl exposes only an IPv6 tunnel address; `status_server.cpp` binds
  `AF_INET`).
- **Fantom over USB-C into the phone/iPad** — MIDI *and* USB audio at once.
  Still the main go/no-go.
- **Backgrounding.** `UIBackgroundModes: audio` is declared and the idle timer
  is disabled while running, but a locked-screen set has not been tested.

## USB-C Ethernet

iOS/iPadOS support class-compliant USB Ethernet adapters natively (an
**Ethernet** pane appears in Settings with DHCP/manual IP), so a wired master
is possible — relevant to the gig-network question below. Caveats: Ethernet
*plus* Fantom USB needs a powered hub, chipset support is broad but not
universal, and Wi-Fi is best turned off rather than trusting route priority.

## Setup on device/simulator

Clips are ~9 GB, far too large to bundle. `config.json` and `clips/` go into
the app's Documents directory (`UIFileSharingEnabled` +
`LSSupportsOpeningDocumentsInPlace`, so Finder and the Files app can write it).
The app `chdir`s to Documents at start, so `clips_dir: "./clips"` resolves
exactly as on macOS — no engine change needed.

The app starts the engine automatically on launch when `config.json` is present,
so there is nothing to tap first.

Pushing files to a real device (the app's Documents container):

    xcrun devicectl device copy to --device <udid> \
      --domain-type appDataContainer --domain-identifier de.welt.midiftbridge.ios \
      --source clips/mp4 --destination Documents/clips/mp4

Launching with the console attached — note that `--console` ties the app's
lifetime to the `devicectl` process, so the app dies when it is killed:

    xcrun devicectl device process launch --device <udid> --console \
      --terminate-existing de.welt.midiftbridge.ios

## Open question — is an iPad the right master?

Wiring the Mac in is what fixed the 2.4 GHz airtime stutter (see
`wlan-panel-stutter.md`). An iPad puts the master back on WLAN. A USB-C
ethernet dongle works, but the same port is carrying Fantom MIDI/audio, so it
means a powered hub. Worth settling before investing in the UI port.
